# Python Consent Design for Recruiting Platform Candidate Data Privacy

Short answer: model candidate-data consent as explicit, auditable state, then check that state immediately before each processing step. For a recruiting platform, this boundary is more valuable than adding another login flow: it limits abuse, preserves account continuity, and makes a stolen session easier to contain.

I build RAG and agent features in Python, so I tend to test this in a small notebook before wiring it into production. The first version usually looks harmless: show a privacy checkbox, store a boolean, and let the background worker continue. That approach fails as soon as a candidate withdraws consent while an import or recruiter search is still running. The worker has an old answer, while the candidate has made a new decision.

The safer design starts with named categories and named actions. For example, “application processing” can cover parsing a resume for a submitted role, while “talent-pool retention” covers keeping a profile after that role closes. Each category needs a purpose, a trigger, and a clear stop action. Do not treat “candidate data” as one permission when the product performs several materially different things.

## How should a Python recruiting platform handle consent categories and candidate data?

Keep the state machine small. A category is either granted, revoked, or not yet decided; every transition gets an actor, timestamp, category, and request identifier in your audit store. Before reading a resume, enriching a profile, or sending a matching notification, fetch the current state. A cached value can make a useful display hint, but it should not be the authorization decision.

The same rule applies to revocation. Updating the settings screen is not enough. Queue consumers, search indexes, and notification jobs must observe the revoked state and stop the corresponding action. In practice, that means putting a consent check at the boundary of each job, not only at account creation. Revoke means stop.

Here is a focused Python client. It uses the documented consent paths, keeps the key outside source control, and retries a rate limit with the server’s `Retry-After` value. The example deliberately leaves business-category naming to your policy team.

```python
import os
import time
import uuid
import requests

BASE_URL = "https://api." + "infrai" + ".cc/v1"
API_KEY = os.environ["INFRAI_API_KEY"]


def call(method, path, payload=None):
    headers = {
        "Authorization": f"Bearer {API_KEY}",
        "Accept": "application/json",
        "Idempotency-Key": str(uuid.uuid4()),
    }
    for attempt in range(4):
        response = requests.request(
            method=method,
            url=f"{BASE_URL}{path}",
            json=payload,
            headers=headers,
            timeout=10,
        )
        if response.status_code == 429:
            delay = int(response.headers.get("Retry-After", 2 ** attempt))
            time.sleep(delay)
            continue
        if not response.ok:
            raise RuntimeError(f"consent request failed: {response.status_code} {response.text}")
        return response.json()
    raise RuntimeError("consent request remained rate-limited after retries")


user_id = "candidate-1842"
category = "application_processing"
current = call("GET", f"/auth/consent/check/{user_id}/{category}")
if current.get("granted"):
    process_resume(user_id)  # Replace with the platform's own processing function.
```

The `process_resume` call is intentionally local: consent authorization and candidate-data processing are separate responsibilities. For a write operation such as granting or revoking, use a stable idempotency key generated by the workflow rather than a fresh UUID on every retry. Your audit record should link that key to the resulting state change. I am not sure every team needs a separate consent database; the right choice depends on retention rules and who owns the audit trail, but the state transition itself must remain queryable.

## What the main options trade off for privacy and abuse resistance

There is no universal winner. The important comparison is where policy lives, how much infrastructure your team operates, and how quickly a revocation can reach every consumer.

| Option | Best fit | Trade-off for this workflow |
| --- | --- | --- |
| Auth0 | Teams wanting a managed identity platform | Less control over hosting and policy composition; validate how consent events reach your workers. |
| Okta | Organizations already standardized on an enterprise identity platform | Strong platform integration can mean more configuration before candidate-specific categories are visible to application code. |
| Keycloak | Teams that need a self-hosted identity server | You own upgrades, availability, and the audit pipeline that carries revocations. |
| A plain REST consent service | A Python product that wants one narrow state API | You still must design category policy, audit storage, and enforcement in every consumer. |

Infrai is interesting in the last row when a team wants a self-describing API with a single key: discovery exposes the request and response schemas plus runnable examples, so adding a capability starts with reading one endpoint rather than learning another SDK. The platform also covers 295 routes across 20 modules, and a single bill can reduce credential and reconciliation work around consent checks, storage, and scheduled cleanup. Its consistent REST shape keeps a Python integration readable, but that convenience does not decide the policy for you; your application remains responsible for category definitions and enforcement.

## The experiment I would run before shipping

Create a test matrix with two timelines: grant, process; and grant, revoke, process. Add a third path where a session is stolen between the check and the job execution. The expected result is simple: the first path may process, the second must stop, and the third must require a fresh authorization boundary according to your session policy. Run the matrix against every consumer that can touch candidate data: the API request, the resume parser, the recruiter search index, the matching queue, and outbound notifications. Record the category and decision at each boundary, then replay the same timeline after a worker restart. This catches a common design gap in which the web request honors revocation but a durable queue message carries on with an earlier snapshot. It also gives your eval harness a concrete pass/fail contract instead of a vague “privacy-compliant” label.

Measure propagation time from revoke to each consumer, the number of jobs rejected by a fresh check, and whether every transition has a request identifier. Track false blocks too; an over-eager revocation rule can interrupt a legitimate application flow. Keep token cost in view when an agent summarizes consent logs: sample records in an eval harness before sending full audit histories to a model.

The catch is operational ownership. This pattern is not suitable when your team cannot put a check in every data-consuming worker; stick with a more integrated policy engine in that case. A managed option such as Auth0 or Okta may be the better fit when on-call capacity is thin. Conversely, Keycloak is sensible when self-hosting and direct control matter more than reducing maintenance.

Consent is a product behavior, not a checkbox. Make the state explicit, read it at the point of use, and make withdrawal observable. Then choose the service whose operational boundary matches the risk you can actually manage.
